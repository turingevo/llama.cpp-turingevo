# 同步上游 (ggml-org/llama.cpp) 最新代码

本仓库有两个 remote：

| remote | 地址 | 用途 |
| --- | --- | --- |
| `origin` | git@github.com:turingevo/llama.cpp-turingevo.git | 自己的 fork，只有 `turingevo` 一个分支 |
| `upstream` | https://github.com/ggml-org/llama.cpp | 官方仓库，只读拉代码，push 已在 git config 里设为 `DISABLED` |

当前状态（2026-11-10）：

- 本地只有 `turingevo` 一个分支，跟踪 `origin/turingevo`，领先远端 354 个提交（还没推）。
- 本地**没有 `master` 镜像分支**，也没有 fetch 过 `upstream`，所以 `upstream/master` 现在还不存在。
- 工作区是从本地另一份克隆 `/media/wmx/ws1/workspace/AI推理部署/llama.cpp` clone 过来的，`origin/turingevo` 是唯一同步点。

上游更新用 merge 不用 rebase：`turingevo` 已经推送过，rebase 会改写历史，只能 force push。

## 一步到位

```sh
git fetch upstream
git switch turingevo
git merge upstream/master
git push
```

`git push` 只会推到 `origin/turingevo`。`upstream` 的 push URL 是 `DISABLED`，误敲 `git push upstream` 也推不上去。

## 逐条说明

```sh
# 1. 拉上游最新提交（不动工作区，第一次会下载整个上游历史，比较慢）
git fetch upstream

# 2. 直接在上游分支上合并，看到的就是上游最新提交
git switch turingevo
git merge upstream/master

# 3. 编译 + 测过之后再推
git push
```

如果习惯保留一个纯镜像分支，可以自己建一个，纯本地用，不需要推：

```sh
git fetch upstream
git branch -f master upstream/master   # 只当书签，合并前看一眼
git merge master                        # 在 turingevo 上执行
```

这样做的坏处是 `master` 和上游可能不同步，忘了更新就会合并到旧代码。直接 `git merge upstream/master` 更省事。

## 冲突处理

冲突基本只会出现在模型代码和 `common/` 目录。处理原则：

- 上游对 SenseNova-U1 的改动优先接受，再检查 `src/models/sensenova-u1.cpp` 里的生成分支是否还在（图构建时按 `cparams.gen_pass` 选 `gen_layers` / `layers` 与 `output_norm_gen` / `output_norm`）
- `tools/sensenova-u1/` 和 `tools/sensenova-server/` 是本地新增目录，上游不会碰，除非 `common/` 或 `src/` 的接口变了
- `turingevo/` 目录上游完全不碰
- 解完冲突后跑 `turingevo/shared/build-all-dev.sh` 和 `turingevo/sensenova/cli.sh` 验证；脚本会重建 `build-alldev/` 并装到 `/home/wmx/software/llamacpp-turingevo/bin/`

## 常见问题

**`git merge upstream/master` 报 `not something we can merge`？**

还没 fetch 过上游，先 `git fetch upstream`。可以用 `git log --oneline -3 upstream/master` 确认 ref 存在。

**要不要用 GitHub 网页上的 Sync fork 按钮？**

只能同步与上游同名的分支，本仓库远端只有 `turingevo`，没有同名分支，所以按钮用不上。全部在本地合并，再 `git push` 推 `turingevo` 分支。

**merge 之后编译报错？**

大多是上游改了 `common/` 或 `src/` 的内部接口，而本地新增代码还在用旧签名。先看 `git status` 里本地改动文件，再到上游对应的 `src/` / `common/` 头文件里找新签名。改完重跑 `build-all-dev.sh`。
